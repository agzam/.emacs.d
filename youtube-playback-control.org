* Synopsis
Watching YT through mpv+yt-dlp is laggy and degrading: YouTube enforces
SABR streaming and PO tokens, FFmpeg cannot consume SABR, and mpv's
pipeline is ytdl_hook extraction + FFmpeg streaming, so client fallbacks
land on throttled or low-quality formats. Plan: control browser-native
playback from Emacs instead - navegosa grows a media-control layer (JXA
transport on macOS and MPRIS/dbus transport on Linux, both validated
E2E). mpv keeps local files/subed/non-YT, with an optional no-cookie
patch-up. One transient key-set mirroring the existing mpv-transient.

* Verified findings
macOS/JXA (E2E against live Brave, this machine):
- [confirmed] osascript JXA round-trip ~145ms including process spawn;
  pause + seek -5s + rate 1.5x batched in one call, state returned.
- [confirmed] Background-tab video fully controllable via tab.execute
  while another tab stays active; no focus needed.
- [confirmed] Apple-Events JS runs in an isolated world: page JS is
  invisible (movie_player API methods undefined), DOM fully accessible,
  cross-call window.* state persists (jump-to-link precedent).
- [confirmed] DOM control surface suffices: video element
  (play/pause/currentTime/playbackRate/volume/muted) + YT buttons
  .ytp-subtitles-button, .ytp-next-button, .ytp-prev-button all present.
- [confirmed] tab.execute into a discarded (Memory Saver) tab hangs
  indefinitely - the stale YT tab did exactly that. Playing tabs are
  never discarded.
- [confirmed] JXA win.tabs.push(new Tab) activates the new tab; restore
  activeTabIndex explicitly when opening in background.
- [confirmed] "Allow JavaScript from Apple Events" already enabled in
  Brave on this machine.

Stage-1 E2E additions (2026-08-05, live Brave + live Emacs):
- [confirmed] A never-focused background YT tab defers media load:
  video element exists with readyState 0, play() accepted but no data
  loads until the tab is visible once (Page Visibility gating by YT).
  mediaCommand returns a distinct error for it; navegosa-media-open-tab
  is the escape hatch. Once a tab has been visible, background control
  works fully.
- [confirmed] subsToggle via .ytp-subtitles-button works from the
  isolated world (aria-pressed false->true->false on a captioned
  video). The button is inert on videos without captions.
- [confirmed] next navigates SPA-style; playback continues in the
  background tab and the new video starts unmuted (muted does not
  survive navigation). prev is inert outside playlist/watch-history
  context.
- [confirmed] Timeout guard proven against a real discarded tab:
  osascript killed at 3.0s, clean user-error, no leftover processes.
  Same guard covered a transient mid-session "video not loaded" blip
  (YT briefly swapped the media element after a rate change).
- [confirmed] In-page command latency 12-26ms; the ~150ms round trip
  is osascript spawn. Batched command+state-read confirmed at that
  cost.
- [confirmed] Elisp lane: async dispatch + echo, copy-url (&t=743s
  exact), retry-once flow (invalid index -> relocate -> discarded tab
  -> guard -> single terminal message, 3.3s) all verified in the live
  session, then unloaded with autoload stubs restored.

Linux (docs-verified 2026-08-04; superseded where noted by the live
probes below):

- [confirmed] MPRIS is native in Chromium-family and Firefox once media

Stage-3 MPRIS probes (2026-08-05, live Brave + live Emacs, Linux box;
scratch tab, near-silent volume, all state restored via unwind-protect):
- [confirmed] dbus.el in-process channel works from the live session:
  property read ~1.2ms, Metadata read ~1.1ms - two orders of magnitude
  under the JXA ~150ms spawn.
- [confirmed] Tab-level mute (Mute site) suppresses the media session
  entirely: with the muted tab playing, the player object stays
  Stopped/empty (CanPlay false, no metadata, Position 0). Unmuting
  registers it within a second. Chromium exposes MPRIS only for
  audible playback - muted media is invisible and uncontrollable, so
  the probe protocol is near-silent player volume, never tab mute,
  and a mute command cannot exist on this lane.
- [confirmed] The bus name (org.mpris.MediaPlayer2.brave.instancePID)
  lingers in Stopped state after media ends - it pre-existed the
  scratch tab. Discovery must filter by PlaybackStatus Playing/Paused,
  never by name presence.
- [confirmed] Rate writes ignored: set 1.5 -> readback 1.0, position
  advanced 1.006s per wall-clock second; MinimumRate = MaximumRate =
  1.0 advertises the constraint.
- [confirmed] Volume property inert on Brave: reads 1.0 with the
  player slider at 5%, write 0.5 bounces back to 1.0. No volume
  control, no mute detection.
- [confirmed] No xesam:url: metadata keys are exactly artUrl, length,
  trackid, album, artist, title. Timestamped-URL copy is impossible
  over MPRIS on Chromium-family; y degrades to an honest error.
  (Firefox reportedly exposes xesam:url - unverified, no Firefox
  here.)
- [confirmed] Relative Seek is hijacked by the page's MediaSession
  seek handlers: +10s request lands +5.15s, +4s lands +5.25s, -10s
  lands -4.81s (YT's ~5s handler step wins). SetPosition(trackid,
  pos) is exact to the microsecond - the backend implements all
  seeking as SetPosition math (Position ± delta clamped to
  [0, mpris:length]).
- [confirmed] PlayPause round-trips cleanly (PlaybackStatus flips
  within 0.4s); Position ticks continuously while playing, freezes
  while paused.
- [confirmed] CanGoNext/CanGoPrevious false on a plain watch page -
  YT registers next/prev MediaSession handlers only in
  playlist/queue context. Next/Previous must be guarded by the Can*
  props with honest errors.
- [confirmed] Metadata carries xesam:title + xesam:artist (channel) +
  mpris:length + mpris:artUrl - echo line feasible sans volume.
- [confirmed] Subtitles and theater have no MPRIS surface at all
  (spec defines no such members; nothing site-specific leaks
  through) - degrade honestly.

Stage-6 probes (2026-08-05, live Brave + Hyprland 0.56 + PipeWire,
Linux box):
- [confirmed] Key injection by focus-bouncing at the shell level
  (activate browser, type, return) is a dead end regardless of speed:
  kernel autorepeat routes the user's held key into whichever window
  holds focus mid-bounce (k pausing YT, Vimium eating letters), and
  Chromium ignores X11 XSendEvent-style unfocused synthetic input
  anyway. Wayland has no unfocused-targeting either (ydotool is
  focused-window-only).
- [confirmed] Hyprland sendshortcut delivers a key to a window by
  address, but Chromium (spec-correct Wayland client) discards keys
  without wl_keyboard focus: bare sendshortcut silently no-ops. The
  working pattern is one batched IPC - focuswindow target ;
  sendshortcut ; focuswindow back - milliseconds, user-confirmed
  imperceptible. hyprctl answers "ok" either way; delivery cannot be
  verified from the exit status.
- [confirmed] Hyprland resolves bare keysyms only at the unshifted
  keymap level: "greater" fails ("key not found"), SHIFT,period
  delivers >. Shifted chars need explicit MOD,KEY specs.
- [confirmed] Window targeting: MPRIS xesam:title is a verbatim
  substring of the Hyprland window title ("<title> - YouTube -
  Brave") while the video tab is frontmost in its window; a
  backgrounded tab breaks the match, which is the correct honest
  refusal (keys would land in the wrong tab).
- [confirmed] PA-level mute is invisible to the browser: MPRIS
  session stays registered, PlaybackStatus Playing, Position ticking
  through the mute. Tab mute deregisters (stage-3 finding); the
  asymmetry is what makes m possible on Linux.
- [confirmed] Brave's sink-input (application.name "Brave", binary
  "brave", media.name a generic "Playback" - no per-tab identity)
  exists only while audio flows: appears on play, survives a short
  pause, gone after longer idle. pactl -f json works; relative
  set-sink-input-volume steps are percentage points; PA volume is
  independent of YT's player slider (gains multiply).
- [confirmed] pactl per-pulse cost is a few ms with no focus
  movement: held K/J through the transient glides smoothly
  (user-confirmed), where any key-injection scheme would strobe
  focus at autorepeat rate.
- [confirmed] Injected page keys hit the active tab exactly like
  typing: Vimium-C (installed here) must exclude the site or its
  default t = new-tab shadows theater. User excluded youtube.com;
  c/t/</> then land on the player. c is inert on caption-less
  videos (stage-1 finding, still true via keys).

* Design decisions
- DOM-only control, no page JS API - forced by the isolated world.
- Tab discovery: URL prefilter (defcustom regex list: youtube, youtu.be,
  vimeo, twitch, ...) -> probe only candidates, each probe
  timeout-guarded -> cache (winIdx . tabIdx). Never blind-probe all tabs
  (discarded-tab hang). On command failure: invalidate cache, re-locate
  once, retry.
- Commands async fire-and-forget (make-process); every JS command
  returns full state {time, duration, rate, paused, volume, muted,
  title, url} so Emacs can echo "12:34/56:07 1.5x" from a callback.
- Package ships commands; transient + dispatcher live in emacs-lab
  config (same split as mpv.el / mpv-transient today).
- One transient, not parallel ones (user decision): mpv-transient
  morphed into media-transient
  (agzam/emacs-lab:modules/web-browsing/autoload/media.el) with
  per-backend groups gated by :if, the expreg-transient pattern
  (agzam/emacs-lab:modules/general/autoload/expreg.el). Same keys in
  every group = one muscle memory; guarded by a key-mirror test.
- Seek/speed/volume steps mirror mpv-transient semantics, steps as
  defcustoms.
- Stage order: mac browser lane -> config integration -> Linux lane (on
  the Linux machine) -> mpv patch-up.
